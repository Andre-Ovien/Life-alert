# Flutter frontend boundary

The human selected Flutter for future Android/iOS and authorized an actual structure foundation. The app source is in [mobile](mobile/), with Android/iOS runner projects, role-aware demo navigation, 46 consumer route contracts, grouped features, shared screen placeholders and disabled API boundaries. This is **not** finished visual design or a functioning care/emergency application.

Designer handoff:

- [Complete screen list](../docs/SCREEN-LIST.md): 65 purposeful screens, split into 46 consumer and 19 separate operations screens.
- [Detailed screen specification](../docs/DESIGNER-HANDOFF.md): actions, entry/exit, permissions, accessibility, routes and PRD references.
- [Required state checklist](../docs/SCREEN-STATE-CHECKLIST.csv): named conditions mapped to their owning screens, not extra screen counts.
- [Designed PDF](../docs/exports/Life-alert-Flutter-Screen-Design-Handoff-v0.1.pdf).

Parent/authorized caregiver and linked-child Flutter surfaces are confirmed. Staff/coordinator/responder/accommodation/admin surface platform remains TBD; operations are not consumer app tabs. Invited caregiver permissions, production identity, secure pairing and real integrations need approved contracts. Child help never requires incident-time adult login or approval.

Use `mobile/README.md` to run the non-operational preview and its tests. Further backend work remains separately authorized; this frontend task did not modify backend features.
